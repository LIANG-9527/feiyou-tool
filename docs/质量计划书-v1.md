# site_audit 质量计划书 v1

- 版本：v1.0
- 日期：2026-09-03
- 作者：老周（技术 owner）
- 适用代码：geo-query-agent 仓库，site_audit 子包（基线提交 380b403）
- 代码现状（盘点实测）：.py 共 8091 行；检查项 46 个（tech 13 / ai 11 / content 8 / auth 7 / b2b 7），其中规则项 37 个、AI 依赖项 9 个（AI 引擎未配置时走 SKIP 降级，见 b2b.py:161/180/199、ai_friendly.py:310/335、content.py:112、authority.py:171/190/209）

本计划书只定义可执行的验收标准。每条标准写清「怎么测、怎么算过」。不设无法测量的目标。

---

## 标准一：确定性——同一输入，同一结果

目标：任何一次诊断，只要输入（目标站页面内容）不变，46 项检查结论必须完全一致。前后对比报告因此才具备验收凭证效力。

具体标准：

1. **LLM 温度锁定**：`AIEngine` 全部调用 temperature=0（已落地，runner.py:44 硬编码，ai_engine.py:63 默认值为 0）。
2. **Prompt 版本化**：`site_audit/core/ai_engine.py` 增加模块级常量 `PROMPT_VERSION`（如 `"geo-v1.0"`），10 个 check_* 方法的 system/user prompt 任何改动必须同步递增版本号；版本号写入每次诊断的 JSON 报告（`core/scorer.py` 的 `build_report` 输出增加 `prompt_version` 字段）。
3. **快照留存**：每次诊断把每个被检页面的关键内容（URL、final_url、status_code、抽取后的结构化文本——即 `_extract_content()` 的产出）和每个 AI 项的原始 LLM 响应，落盘到 `output/audit/snapshots/{domain}_{ts}/`，与 HTML/JSON 报告同名同目录层级。
4. **复检重放**：复检对比必须基于首次诊断的快照重新计算，而不是重新抓站。

**怎么测**：任取 3 个站，诊断一次取快照，用快照重放 3 次。
**怎么算过**：3 次重放的 46 项 status 与 scorer 总分零差异（diff 为空）；JSON 报告里能读到 `prompt_version`；快照目录文件齐全（每页一个结构化文本 + 每个 AI 项一个 LLM 原始响应）。

## 标准二：准确性——规则项 100% 复现，AI 项抽检一致率 ≥85%

1. **规则项（37 个）**：对同一快照重复运行，每项的 status 与证据描述必须 100% 一致。
   - **怎么测**：baseline 库 20 站快照双跑（连续跑两遍）。
   - **怎么算过**：20 站 × 37 项 = 740 个结果，逐项 diff，不一致数 = 0。
2. **AI 依赖项（9 个）**：AI 判定结论与人工复核结论的一致率 ≥85%。
   - **怎么测**：从 baseline 库抽 5 站，对 9 个 AI 项共 45 个判定，人工逐项复核「status 判得对不对」。
   - **怎么算过**：45 个判定中人工认可数 ≥ 39（≥85%）。低于 85% 的项，prompt 必须修订后重测，直到达标或该项降级为「仅提示不计分」。

---

## 标准三：回归 baseline——改代码必回归，无未解释差异

1. **baseline 库**：选取 20 个真实站点（覆盖模板站/SaaS 建站/自建站、快站/慢站、有内页/无内页），每站存：页面快照、期望诊断结果 JSON（46 项 status + 总分 + 等级）。
2. **回归入口**：新增 `scripts/regression.py`，对 20 站快照跑全套检查并与期望结果逐项对比，输出差异报告。
3. **执行时机**：site_audit 子包任何代码改动（含 prompt 改动）提交前必须跑回归。

**怎么测**：改动提交前运行 `python scripts/regression.py`。
**怎么算过**：20 站全部跑通；规则项差异数 = 0，或每一处差异在 commit message 中逐项说明原因（如「tech-13 断链判定逻辑修正，hcqycs.com 由 warn 变 fail 属预期」）。出现未解释差异 = 不通过，禁止提交。

## 标准四：爬虫合规——robots 遵守 + 限速 + UA 声明

现状：`core/crawler.py` 的 `SiteCrawler`（max_pages=12、max_workers=4）不解析 robots.txt、无请求间隔；`core/fetcher.py` 只把 robots.txt 当检查对象（tech-02），不当遵守对象。

1. **robots 遵守**：`SiteCrawler.crawl()` 抓取任何页面前，先用 `urllib.robotparser` 解析目标站 robots.txt；disallow 的路径不抓。
2. **限速**：同一域名请求间隔 ≥ 1 秒（含 4 个 worker 合计，用令牌桶或全局锁实现，不是每线程 1 秒）。
3. **UA 声明**：`fetcher.DEFAULT_HEADERS` 的 User-Agent 改为可识别身份 + 联系方式，格式：`GEO-Audit-Bot/1.0 (+https://极联股份官网/bot)`。

**怎么测**：① 对一个 robots.txt 中 disallow 了 `/news/` 的站跑诊断，检查抓取日志；② 对任一站抓 12 页，从日志统计同域名请求间隔。
**怎么算过**：disallow 路径抓取次数 = 0；同域名请求间隔 P95 ≥ 1 秒；目标站响应日志里能看到新 UA。

---

## 标准五：报告 SLA——单站诊断 P95 ≤ 60 秒

现状实测：单站诊断 20–40 秒（串行抓取 12 页 + 9 个 AI 项串行调用）。

1. **时限**：从 `/api/audit` 收到请求到报告 JSON 可下载，P95 ≤ 60 秒。
2. **降级**：单页抓取超时 15 秒（fetcher 现状）跳过该页；单站总耗时预算 90 秒硬上限，超出部分未完成项标 SKIP，不允许无限挂起。
3. **并行化**：AI 项调用从串行改为并行（`asyncio.gather` 或线程池），这是达标的必要手段，不是优化项。

**怎么测**：对 baseline 库 20 站各诊断一次，记录端到端耗时（runner 入口到 JSON 落盘）。
**怎么算过**：20 站 P95 ≤ 60 秒；无一站超过 90 秒硬上限；超时降级项在报告中正确标记 SKIP 而非报错。

## 验收方式

- 每条标准的测试脚本/记录落盘：`scripts/regression.py`、`output/audit/snapshots/`、baseline 库存于 `tests/baseline/`（快照 + 期望 JSON）。
- 五项标准的通过状态汇总为一页《质量验收记录》，由 LIANG 花 10 分钟过一遍：全绿 = v1 质量基线达成；任何一项不通过，对应功能不进跑单版本。
- 本计划书为 v1 完整定义，不存在「完整版」后续文档；标准本身如需变更，走 backlog 记录（原因 + 影响 + 下一版本安排）。
